## 1. 검수해 주셨으면 하는 것

우선순위 순입니다.

### (A) 발열 수정이 옳은가 — 제일 중요

실기기 발열 제보를 받고, 무한 CSS 애니메이션 다섯 개를 "합성 불가 속성 →
합성 가능 속성"으로 바꿨습니다. 커밋 `7a960b3`.

| 대상 | 전 | 후 |
| --- | --- | --- |
| `.screen-play::before` (전체화면 테두리 경고 2종) | `box-shadow` 애니 | 고정 그림자 + `opacity` 애니 |
| `.board-frame.is-fever` / `.is-fever-expiring` | `box-shadow` 애니 | 고정. 숨쉬기는 `.board`의 `filter`가 담당 |
| `.time-readout.is-warning` | `drop-shadow` **반경** 애니 | 고정 `drop-shadow` |
| `#time-value` (타이머 숫자) | `color` 애니 | `filter: brightness/saturate` 애니 |
| `#retry-button` | `transform` + `box-shadow` | `transform`만 |

**제가 측정한 값** (Chromium, CPU 6배 스로틀, 390×780, 5초, CDP Tracing으로
`Paint`/`RasterTask` 직접 집계):

```
상태            메인CPU   Paint    Raster
조용한 플레이      0.4%      0회      0ms
콤보 60 티어     0.6%      0회      0ms
피버           19.4%    600회   1043ms   -> 수정 후 0.5% / 0회 / 0ms
마지막 30초      29.8%    897회    506ms   -> 수정 후 0.6% / 0회 / 0ms
결과 화면        37.2%   1210회    672ms   -> 수정 후 0.5% / 0회 / 0ms
```

**검증해 주세요.**
1. 이 수치가 재현되는지. 재현 스크립트는 안 커밋했습니다(제 작업용 임시
   파일). 직접 짜서 재보시는 편이 검수로서 낫습니다.
2. **측정 방법 자체가 타당한가.** 저는 한 번 틀렸습니다 — 프레임을 세려고
   넣은 `requestAnimationFrame` 루프가 모든 CSS 애니메이션을 메인 스레드로
   끌어내려서, 같은 상태를 11.2%와 1.6%로 다르게 쟀습니다. 최종 수치는 rAF
   없이 잰 것이지만, **다른 오염이 남아 있을 수 있습니다.**
3. **가장 큰 한계: GPU를 못 쟀습니다.** `TaskDuration`은 메인 스레드만
   봅니다. 폰 발열의 상당 부분은 GPU 래스터/합성인데 이 환경에서 직접 잴
   방법을 못 찾았습니다. "다시 그리기를 없앴으니 GPU도 준다"는 제 추론이고,
   **증명은 안 했습니다.** 이 추론이 맞는지, 혹은 전체화면 `opacity` 레이어
   3장이 동시에 합성되는 지금 상태가 오히려 GPU에 나쁘지 않은지 봐주세요.
   (`play-edge-alarm`, `time-danger-breathe`, `final-rush-beat`가 마지막
   30초에 동시에 돕니다. 각각 390×780 전체 크기입니다.)
4. **눈에 보이는 결과가 실제로 같은가.** 저는 계산된 값으로만 대조했습니다:
   - 화면 테두리: 알파 0.12 × opacity 0.25 = 예전 0.03 (같음). 다만 blur
     반경과 spread는 최댓값으로 고정됐습니다(22px 0 → 28px 2px). 저는 이걸
     "사실상 같다"고 판단했는데, **약한 순간에 번짐이 더 넓어 보일 수
     있습니다.** 실제 화면으로 봐주세요.
   - 타이머 숫자: `brightness(1.15) saturate(.82)`가 `#DD6032`를
     `rgb(233,115,71)`로 만듭니다. 원래 목표색 `#f08050`은 `rgb(240,128,80)`,
     거리 17입니다. 이게 허용 가능한 근사인지.

**제가 이 수정에서 회귀를 두 개 냈다가 커밋 전에 잡았습니다.** 둘 다 원인이
같습니다 — CSS 애니메이션은 평범한 선언을 항상 이기므로, `keyframes` 안에만
있던 값은 애니메이션을 걷어내는 순간 사라집니다.
- 피버 분홍 후광이 통째로 소실 (특이도 싸움에서 밀림)
- 타이머 숫자가 주홍 `#DD6032` → 진홍 `#e03150`으로 변경

**같은 함정이 남은 곳이 더 있을 수 있습니다.** `keyframes`에만 존재하는 값에
의존하는 다른 규칙이 있는지 훑어봐 주세요. 저는 이 다섯 개만 봤습니다.

커밋 `33929a0`. `.ait` 10.4MB → 9.1MB.

**검증해 주세요.**

### (D) 제가 안 본 곳

솔직히 이번 검수에서 **안 본 영역**입니다. 여기서 문제가 나올 확률이 제일
높습니다.

- **안드로이드 빌드** — Capacitor 쪽은 이번에 한 번도 안 돌려봤습니다.
  CSS 변경이 WebView 버전에 따라 다르게 나올 수 있습니다.
- **iOS(토스 앱 내 WebKit)** — 실기기도 시뮬레이터도 못 씁니다. 제 측정은
  전부 Chromium입니다. `-webkit-text-stroke`, `backdrop-filter`,
  `filter: drop-shadow` 모두 WebKit에서 다르게 굴 수 있습니다.
- **저사양 기기** — CPU 6배 스로틀은 흉내일 뿐입니다.
- **접근성** — 스크린리더, 대비, 터치 타겟 크기를 이번에 안 봤습니다.
- **장시간 플레이** — 메모리 누수. 20판 연속 같은 건 안 돌려봤습니다.
  (`ui.js`에 타이머/리스너가 많습니다)
- **동시성** — 광고 중 백그라운드 전환, 판갈이 도중 일시정지, 카드 개봉 중
  뒤로가기 같은 겹침. 일부만 봤습니다.

## 2. 제품으로서의 상태 (점수 매기실 때 참고)

숫자를 부풀리지 않겠습니다.

**실제 사용 규모**
- 어제 하루 인앱 광고 노출 **29회**, 예상 수익 **3,259원**
- 그중 21회가 "30초 더"(TIME UP 이어하기). 이건 한 판에 한 번만 뜨므로
  = 어제 광고를 보고 이어한 판이 21판
- 리뷰는 있지만 **전부 제작자의 지인**입니다 (제작자 본인 진술)

**즉, 유의미한 사용자 데이터가 없습니다.** 이번 주에 한 게임성 결정(사다리
B, 꼬리 구제, 난이도 조정)은 전부 **헤드리스 시뮬레이터**(`tools/classic-balance-sim.mjs`)
결과에 기반합니다. 실제 사람이 아닙니다.

**로딩** (Chromium, 느린 4G + CPU 4배)
- 첫 그림 2.65초 / 시작 버튼 6.46초 / 네트워크 조용 16.7초, 총 2.6MB
- 토스 안에서는 번들이 로컬이라 다릅니다. 대신 첫 설치 다운로드가 9.1MB

**이번 주에 붙인 재방문 장치 3종** — 도전장, 카드 수집, 다음 목표 줄.
셋 다 **이미 들어온 사람**에게만 작동합니다. 유입이 0에 가까운 지금
상황에서 이 셋이 옳은 투자였는지도 평가해 주시면 좋겠습니다.

## 3. 점수를 매기신다면

이런 축이면 유용할 것 같습니다. 후한 점수는 필요 없습니다.

1. **코드 건전성** — 34k줄 바닐라 JS, 번들러 없음, CSS 4파일 중첩. 특히
   CSS 특이도 싸움(제가 회귀 2개를 낸 그 지점)이 구조적 문제인지
2. **이 발열 수정이 실제로 옳은가** — 방법·수치·부작용
3. **테스트가 실제로 뭘 지키는가** — 247개가 많아 보이지만, 회귀를 잡은 건
   테스트가 아니라 제 수동 대조였습니다. 그게 시사하는 바
4. **제품으로서의 생존 가능성** — 유입 0, 데이터 없음, 수익 하루 3천원
5. **다음에 뭘 해야 하는가** — 제 의견은 "게임을 더 다듬는 건 지금 수익이
   안 나는 투자, 유입이 먼저"인데 반박해 주셔도 좋습니다
